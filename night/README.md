# night/ — 夜間バッチ審査の作業場

gate1_queue の未審査銘柄を約10社ずつのチャンクに割り、夜間に門2審査（完成パック生成）を回すための道具一式。

- `chunkNN.txt` — 審査する銘柄リスト（10社/枚・計約150社）
- `agent_prompt_template.txt` — 審査官エージェントへの指示文。**正本は index.html Ⅱ実行手順「3 審査」の門2審査プロトコル**——正本を改定したら本テンプレも必ず同期すること（二重正本ドリフト防止）
- `agent_prompt_template_jp.txt` — 日本株版（2026-07新設）。**原本PDF優先**で自力採取し（EDINET直配信の有報→決算短信→irbank。EDINET_DB MCPには依存しない＝接続不安定かつ生ROICがアーティファクトの発生源）、JP必須規約（ROIC三点＝現金非控除・60%上限、roicEx必須、TTM PER）を強制。一括再審査は「日本株を夜間審査して」だけでよい（`make_chunks.py` が `jp_chunkNN.txt` を作るのでコード貼りは不要）。EDINET_DB MCPが未接続のときの代替採取経路も明記済み
- `progress.json` — 進行表。`fetched`（採取済）→ `pending_review`（審査待ち）→ `reviewed`（審査済）
- `kenshi_helper.py` — 検死用: companyfacts.zip から年次系列（売上/営利/OCF/capex/株数…）を機械表示
- `make_copypage.py` — 完成パックのコピー用ページ生成
- `make_chunks.py` — 未審査分のチャンク自動生成（queue/椅子/棚/backlog−審査済−SKIP。10社/枚・連番継続）＋日本株の `jp_chunkNN.txt` と `out/packs_index.json`（門の一括取込ボタン用の目録）を更新
- `score_all.js` — **門の compute() をそのまま走らせて out/ の全パックを採点する検証器**（`node night/score_all.js`）。採点ロジックには触れずDOMだけ差し替えるので、門が画面で出す点と同じものが出る＝二重実装を作らない。`--jp` / `--us` / `--only MSFT,6920` / `--set dom=100`（感度分析。ただし全パックを上書きする粗い道具）。出力は `out/score_all.json`。「基準を変えたら実際に誰がどう動くか」を推測でなく実測で出すための道具。**Ωの点だけでなく三段関門（Ω75+ ∧ 門X4条件 ∧ 絶対MOAT指数75+）の合否まで門と同じ関数（`ccfXJudge` / `ccfMoatGate`）で判定する**ので、🟢投下可が何社になるかがそのまま出る。妥当性の確認は、素の実行で米国のΩ75+に V/ASML/KLAC/NVDA/MSFT/MA/TSM/ADBE/RMD/IDXX 等が並ぶこと
- `audit_moat.py` — **堀5本(dom/irr/rep/dur/moatW)の「根拠の質」を全パックで点検する**（`python3 night/audit_moat.py` / `--q75` / `--list`）。v9.9.39で堀のふるい（絶対MOAT指数≥75を新規投下の第三の関門）を入れたが、**ふるいは入力の質を超えられない**——測っていない値で優良企業を切ったら堀ではなく審査の手抜きを罰していることになる。dom が入っているのに根拠が空／定性表現のみ（"a leader"）／「原本にシェア開示なし」と自認しながら数字が入っている、dom 空欄なのに理由が_metaに無い、moatW 空欄、上位N社の構造が未確認（v9.9.38の刻みは構造で決まる）——を仕分けて再監査の作業リストを出す。初回実測（2026-07-29）はΩ75+の25社中◎が1社（MCO）のみ
- `audit_roic.py` — **ROICが「分母の縮退」で発散していないかの点検**（`python3 night/audit_roic.py` / `--q70` / `--list`）。門のroicはのれん除外版＝NOPAT÷(自己資本+有利子負債−のれん−無形)で、買収で伸びた会社は自己資本の大半がのれん＋無形のため**分母が自己資本のごく一部まで縮退し、わずかな推定誤差が桁で暴れる**。実測: NJR 16.5→真値6.6(負債3.6十億$欠落) / HEI 93.0→null(ICが自己資本の31%・5年系列が51-81%で振れ識別力なし) / APH 163.4→28.0 / COLL 160.3→41.3 / TRN 63.1→8.0。**ただしLDOS 33.8→58.4・MRK 21.7→34.3・WM 17.9→22.3と逆に低く出ていた社もある**——「高すぎる値だけ疑う」では取りこぼす。※**高いROICそのものは異常ではない**（roic=事業の質 / roicg=買収規律の乖離は門が意図して作っており、roicGap>15を買収依存として減点する設計）。この一覧は再監査の作業リストであって有罪判決ではない
- `hist_valuation.py` — **自己相対バリュエーションの採取器**（2026-08-09新設・事前登録 `out/hist_valuation_prereg.json` 用）。
  `python3 night/hist_valuation.py --asof 2018-07-01 --tickers out/retro_returns_2018.json --out out/hist_val_2018.json` ／
  点検は `--t MSFT,AAPL,KO --asof 2018-07-01` ／ 今日の台帳にも使える `--t MSFT --asof 2026-08-09`。
  この台帳が過去に測った価格の線は**全部横断面**（他社と比べて高いか＝絶対PER・市場相対PER・fairPER倍率）で、
  **その銘柄自身の過去と比べて高いか（自己相対）は一度も測っていなかった**。その穴を埋める。
  出す指標: `pe_pct` `ps_pct` `pfcf_pct`（自社の過去N年の月次分布の何%タイルか）／
  `adj_pe_pct`（**市場調整版**＝自社PER÷S&P500実績PERの自己履歴分位。2009-18は全体が倍率拡大期なので素の分位は
  全員高く出る）／`pe_z` `ps_z`／`spx_pe_pct`（市場水準の1871年以降の分位）。
  - **倍率の分子は時価総額に統一**（PER も PS も PFCF も）。株価側の変換を1箇所にまとめれば間違える場所も1箇所で済む
  - **分割は「今日の株数基準」へ揃えてから割る**: `mcap(M)=close(M)×申告株数(filed=f)×S(f)`（S(f)＝f より後の分割比の累積）。
    Yahoo の close は今日まで調整済みなので、当時の申告株数を素で掛けると**後に分割した社＝勝者ほど倍率が安く出る**
    （retro_per_asof.py が記録している事故の型）。この式は S(M) が約分で消えて**恒等的に当時の時価総額**になる
  - **look-ahead は構造で防ぐ**: 各月に使う決算は `filed ≤ その月末` のものだけ・同じ期に複数申告があれば **filed が最も古い値**・
    価格は**月末が asof 以下**の月足・S&P500の分位も asof 以前だけ。**決算期末では切らない**
  - **欠測をゼロと読まない**（ルール7）: capex タグが1本も無い社は FCF を算出不能にする／純利益が正でない月は分位から外して月数を数える／
    申告が USD でなければ割らない
  - **特別配当・スピンオフで自己履歴が切れていないかを見る**（`max_distrib_pct` / `distrib_break`）。
    分割は単位の付け替えなので補正できるが、**特別配当と分社は会社そのものを小さくする**ので前後の倍率は同じ会社を測っていない。
    close（分割のみ調整）と adjclose（分割＋配当調整）の月次リターンの比＝その月の分配率。実測 **MDLZ 2012-10 に 50%** を検出。
    ⚠**穴がある**——拾えるのは Yahoo が配当調整に織り込んだ分配だけで、**ABT(2013 AbbVie) と HPQ(2015 HPE) は素通りする**。
    `distrib_break=false` は「分社が無かった」ではなく「Yahooの配当調整に現れる大きな分配は無かった」の意味
  - **株数の桁を付け間違えた申告を落とす**（`share_scale_guard`・2026-08-09追加＝`tool_rev` **r2**。2013の点検で発見）。
    同じ会社・同じタグの中で株数が桁で飛ぶ申告が実在する——**QCOM** の2011年の2枚が `1,669,532,005,000株`（正 1.67e9＝×1000）、
    **MOG-A** の2012年以降の10-Qが `45,766,798,000株`（正 45.8e6・10-Kは正しい）、**CSX** の2011-04-20 が `val=1`（一株）、
    ORCL は ×1e6。**956社中57社(6.0%)** が ≥4倍の桁飛びを含んでいた。
    分位は**その社自身の履歴の中の順位**なので、履歴の一部だけが×1000だと**「自己史上いちばん高い」が機械的に作られる**
    ——実測で **MDU の ps_pct が 1.0**・**2018年の VSH の pe_pct が 1.0**＝**この検定が探している信号そのものを捏造していた**。
    時価総額の帯検問では拾えない（桁飛びが履歴の側にあると現在値は正常に見える）。
    → 分割で今日基準へ正規化した**後**に、中央値の clean な10のべき乗ぶんずれる申告（および100倍以上離れる申告）を落とす。
    **推測で桁を戻さない**（CSXの`1`を`1e9`に「直す」のは捏造）。落とした枚数は `shares_scale_dropped`・中身は `diag`。
    ⚠**株数にだけ当てる**——同じ検定をフローに当てると ni の10.6%・ocf の6.4%が鳴るが、中身は BA・AMAT の**本物の減益**だった
    （利益は10倍動きうるので誤りと不振を区別できない）。株数は分割正規化後に10倍動かないので、ここでだけ成立する検問。
    実測の効き: 2013 は45社で落として**分位が動いたのは6社**（CNPは 0.80→**0.95** と上がる＝下げる方向の検問ではない）／
    **2015は23社で15社の分位が動き（STX pe_pct 0.957→0.370）／2018は68社で57社が動く（CTA-PB 0.034→0.784・INOD ps 0.987→0.0）**。
    ⚠**`tool_rev` の無い在庫は r1** ＝この誤りを含む。**版の違う在庫を突き合わせないこと**（「基準の違う二つ」の型）
  - **部分実行は正本を書かない**（2026-08-09・実際に潰してから入れた検問）。`--t` / `--limit` を付けた実行は
    `--out` が無ければ `out/_partial_hist_val_{年}.json` へ書く。既定の出力先は `out/hist_val_{年}.json`
    ＝**そのビンテージの正本**なので、`--t MSFT` の点検を素で回すと961社の在庫が1社で消える
    （CLAUDE.md が記録する `score_all.js --jp/--us が正本を部分集合で上書きしていた`とまったく同じ型）。
    cacheがあれば30秒で復元できるが、**気づかなければ後段の検定が n=1 の在庫を読む**
  - キャッシュ `out/_histval_cache/`（.gitignore済）。**961社の1ビンテージが初回約22分・キャッシュ後は約30秒**なので
    窓や下限を変えた感度分析が安い。`--offline` でキャッシュだけでも回る。
    facts も px も asof に依らないので**2ビンテージ目以降はほぼ無料**（実測: 2013の母集団956社は2018の961社の**完全な部分集合**）
  - ⚠**2013ビンテージは既定の設定では使えない**（実測・在庫を作ったうえでの結論）。
    `pe_pct` の被覆は **2018 75.2% ／ 2015 82.1% ／ 2013 14.6%**。
    原因は自己履歴の長さで、**XBRLが2009年開始・TTMの組み立てにさらに約18ヶ月の助走が要る**ため、
    2013-07時点の自己履歴は**中央値22ヶ月・最長46ヶ月**しかなく、既定の下限36ヶ月で724社が落ちる。
    → **事前登録の「2ビンテージ以上」は 2015 と 2018 で満たすのが素直**。
    2013 を使いたいなら `--min-months` を下げるしかないが、**その値は事前登録の閾値の格子に無い**ので
    下げるなら選択として記録すること（22ヶ月の履歴に対する「分位」がどれだけ意味を持つかは別問題）
- `hist_val_join.py` — **上の在庫に「前方リターン」と「プールの印」を綴じる**（2026-08-09新設・冪等）。
  `python3 night/hist_val_join.py --asof 2018 [--report]`。採取器は asof より後を一切知らない
  （知る経路を作ると look-ahead の穴が増える）ので、リターンとの join は別の道具にした。
  ただし**後段の検定 agent が毎回 join を書くと同じ join が3つできて基準がずれる**ので1本に固定する。
  足す欄: `tr_cagr`(小数・出所のまま) `tr_total` `years` `mdd` `ret_start/end` ／
  `window_full` `quality` `q_opm` `q_fcfpos5` `q_op_all_pos` `q_src` ／ `in_per_inv` `per_xs` `analysis_set`。
  - **窓を揃える**（事前登録 data.forward_return の規則）。`window_full` はそのビンテージの**最頻の窓**と一致するか。
    2018で外れるのは **DBD(3.01年) / EXE(5.5年) / GPOR(5.26年) / APYX(7.59年)** の4社——
    前3社は Chapter11 で普通株が消え、Yahoo の系列が**再上場以降しか無い**。3.01年の年率62.5%を
    8.09年のコホートに混ぜると勝者に見えるが、2018年に買った株主の実現は概ね −100%。
    **行は残して印だけ落とす**（黙って消さない）
  - **質実証プールの式は、そのビンテージで既に使われているものをそのまま使う**（二重実装を作らない）:
    2013/2015 は `retro_cohort_{Y}.json` の `opm≥0.10 ∧ fcf_all_pos ∧ op_all_pos`（retro_build_readlist と同じ）／
    2018 は `retro_features2_2018.json` の `opm≥0.10 ∧ fcfpos5≥5`（retro_price_tail・retro_er_test と同じ。
    実測でCLAUDE.md記載の**質実証プール274社**をそのまま再現する）。
    ⚠**2018には「営業利益全年黒字」の在庫が無い**（features2 が持つ opm/opmD5/streak_opm はどれも別の量）。
    推測で印を付けず `q_op_all_pos=null` にし、header に明記する。同条件を課すと 2013 は −10.4%・2015 は −6.8%
    プールが縮むので、**2018のプールは他の2つより7〜10%ぶん緩い**——基準3を読むときはこの差を承知で読む
  - **単位を変換しない**。`tr_cagr` は出所（retro_returns）のまま小数。同じ量を2つの単位で持つと、いつか片方だけ使われる
  - 在庫の header に `join.caveats` を**数えたうえで**同梱する（別ファイルの覚書は読まれない）。
    2018の中身: z と分位で自己履歴の下限が違う（分位36ヶ月 / z 8ヶ月＝**pe_z が29社、36ヶ月未満の履歴で付く**）／
    倍率は2018-06・リターンは2018-07始まりで1ヶ月ずれる／赤字でPERが定義できない158社／
    **TCJA(2017-12)の一時費用が2018-06時点のTTM純利益に乗る**（MSFT TTM 14.2十億$・PER53.3・自己分位0.958、KO PER130
    ＝pe_pct が高い社の一部は『高い株価』ではなく『一時的に低い利益』を測っている。ps_pct/pfcf_pct はこれを受けない）／生存バイアス
  - **採取器を再実行したら join も再実行する**（採取器は join した欄を持たない生の在庫を書くため）。
    実測で `採取器(--offline 29秒) → join` は**バイト単位で同じファイルを再現する**
- `_histval_crosscheck.py` — 上の自己検算（`python3 night/_histval_crosscheck.py [out/hist_val_2018.json]`）。
  **別実装・別経路の `out/retro_per_2018_all.json` と突き合わせる**。いちばん効くのは検問1
  ——`retro_px ÷ (本器px × 分割倍率)` は「2018年6月→7月の値動き」でなければならない。
  実測: **699社で中央値 1.025（S&P500の2018年7月は+3.6%）・±40%を外れるのは KDP 1社だけ**
  （これは事故ではなく実在の企業行動——2018-07にDr Pepper Snappleが**1株$103.75の特別配当**を払ってKeurigと統合した）
  ＝分割補正が両実装で一致していることの独立な確認。
  ほかに 倍率の水準／EPSタグ版との一致／被覆／生存バイアスの実数／指標どうしの順位相関 を出す
- `validate_jp_packs.py` — 日本株パックの納品検査。`python3 night/validate_jp_packs.py`（コード指定も可）。nmがコード始まりか（＝門のJP検問が発火するか）・ROIC三点（roic/roicEx同値・60%上限・roicg≤roicののれん整合）・TTM PERの符号・様式キー一致（受理キーは門のapplyFieldsから読む）・列挙値/点数域・_meta必須を落とす。**致命があれば審査官へ差し戻す**（そのまま置くと門が取込拒否して審査待ちに溜まる）

出力は `out/{T}_gate_pack.json`（完成パック）。パックは門のⅢ採点機「＋取り込む」へ。
機械値だけのドラフト（`{T}_gate_input.json`）は台帳データではない（CLAUDE.md 絶対のルール2）。
