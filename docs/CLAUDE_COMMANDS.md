## eps欄の定義が台帳内で二つに割れている

- **eps欄の定義が台帳内で二つに割れている（2026-07-30・全件点検で判明・要判断）**:
  `eps` に **TTM実績** を入れているパック（ADBE 93.90）と **通期実績** を入れているパック
  （MSFT/NVDA/DXC/TSM/SAP。evidenceに「機械算出…（TTMではなく通期実績）」と明記）が混在する。
  一方 `per` は規約上 **px ÷ TTM実績EPS**。したがって **per = px÷eps はこの台帳では恒等式ではない**。
  - 実害は「検査が誤検出する」形で出た——全件点検の初版がこれを要修正17社として挙げ、うち
    **TSM/SAPは原本根拠つきで確定済の正しい値**だった（TSM: ADR 1単位=普通株5株・px USD/eps TWD、
    SAP: ADS 1単位=普通株1株・px USD/eps EUR）。**MAのroicを古い記録だけ読んで巻き戻した事故と同型**を
    危うく再演するところだった（後から書かれた記録を先に探して回避）
  - 現在の扱い: 門(ブラウザ)側は `_meta` を持てないので **warn** 止まり。
    **端末側の validate_packs.py に厳格版**を置き、`_meta.evidence.per` に基準（TTM/通期・通貨・ADR比）が
    書いてあれば免除、無ければ FAIL とする＝二層で守る
  - **決着（v9.9.57・2026-07-30「あなたの判断でやって」）**: **eps欄の定義は統一しない。代わりに
    価格更新を基準保存式にした。** 根拠——`eps` は **compute() で一切使われない**（採点に効かない）。
    唯一の役割は「価格更新時に per を再計算する」ことだけだった。旧実装は `per = px ÷ eps` を第一に
    置いていたので、通期epsを持つ社では**価格を更新した瞬間に per が TTM基準から通期基準へ黙って
    切り替わっていた**（成長企業では過大・減益企業では過小に振る）。
    → `per_new = per_old × (px_new ÷ px_old)` を第一にした。価格の変化だけを反映し、利益の期間基準に
    触れない。px÷eps は旧pxが無いときだけのフォールバックにし、その場合はmemoに警告を残す。
    **これで eps の定義が割れていても per は壊れない**——欄の統一（全社のTTM EPS再取得）という
    大工事をせずに、事故の経路そのものを塞いだ。eps は以後「参考値・evidenceに基準を明記」で運用する

## 門X未評価の解消

- 門X未評価の解消（2026-07-29の実務メモ）: 門Xは `per>0` が**唯一の必須条件**で、これが無いと E[r] を

  既に記録しているNVDA 2,466→24,304百万株の事故と同型）。

## 門2審査の自動化は GitHub Actions ではなく Routine で回

- **門2審査の自動化は GitHub Actions ではなく Routine で回す（2026-08-10 ユーザー指示「作って」→「5社にして」）**——
  **`.github/workflows/review.yml` は鍵が無いので一度も走っていない**。代わりに Claude の Routine
  `【門】日次 門2審査（自動・5社）`（`trig_015mkv2bccoz87jEjr4c3djU`・cron `0 20 * * 0-4`＝**平日05:00 JST**・
  毎回**新規セッション**・5社／回）が待ち行列の先頭から審査して**PRを出す**。マージは人。
  - **⚠ Routine はモデルを明示しないと環境の既定を継ぐ（2026-08-11・試運転で発覚）**。初回の実走は
    **`claude-sonnet-5` で起動していた**——作成時に model を指定しなかったため。原本PDFを直読して
    刻みの境界を裁く仕事なので、ユーザー明示指示「opus5でエフォート最大でやるようにして」で
    **`claude-opus-5` を固定**した（`update_trigger` の `model`。新規セッションを作る Routine なので次回の発火から効く）。
    **エフォート（思考の深さ）はトリガAPIに欄が無い**ので設定できない——代わりに**プロンプトに
    『1社ごとに ultrathink』と、向きの逆な引用・基準の不一致・規約に無い中間値の3点を必ず立ち止まって
    確かめる指示を入れた**。API設定と同義ではない（プロンプト側のてこ）ことは正直に記録しておく。
    **「急いで5社より根拠の確かな3社」**も明文化した
  - 〔経緯は書庫〕試運転が29分走って痕跡ゼロ・Routine起動のセッションは一覧に出ない＝「毎日空振り」と「毎日何もしていない」が区別できなかった → docs/CLAUDE_ARCHIVE.md L14590
    → **`night/log_review_run.py` が毎回1行を `out/review_runs.json` へ残す**（判定にも採点にも不使用）。
    終わり方は `pr / empty / limit / source_down / discarded / error` の**6語に分ける**
    ——同じ「PR無し」でも意味がまるで違うので、一語にまとめると
    「測っていない」と「測って問題なし」の取り違えを運用の側で作ることになる。
    回転盤に **`reviewrun`（毎営業日・期限4日）**として登録＝残さなければ⚙自動化タブが赤くなる。
    **PRの有無ではなく「走ったか」で測る**（空振りは正常な終わり方で、止まったのとは別物）
  - 〔経緯は書庫〕★手当てが効いていなかった（指示だけ足してOUTCOMESに started が無かった）／started の実装＝印と検出は対・started は結末ではない・JSTは jst_date() に一本化／抜けを unknown で埋めない理由／回転盤は最終日しか見ない → docs/CLAUDE_ARCHIVE.md L14602
  - **⚠ そのログだけは main へ直接 push する。抜け道にならないよう構造で縛った**——
    手順書の「main へ直接コミットしない」は**審査結果（パック）**についての約束だが、
    走行ログは **PRが出ない日にこそ要る**ので PR経由では原理的に残せない。そこで `--push` は
    **作業ツリーを一切使わず**、`hash-object → 一時indexへread-tree → update-index（このパスだけ）
    → write-tree → commit-tree → push <sha>:main` で
    **「origin/main のツリー ＋ out/review_runs.json だけを差し替えた木」**を組む。
    ＝**このツールでは他の1バイトも main へ送れない**（`HEAD:main` を押さないので審査中のブランチも巻き込まない）。
    **注入検査で実証済み**——index.html を書き換え新規ファイルを置き6件をステージした状態で
    `--dry-run` すると、作られるコミットが触るのは `out/review_runs.json` **1件だけ**。
    `--dry-run` はこの性質を誰でも measure し直せるように置いてある（**副作用の無い経路は失敗しても静か**なので、
    性質は文章ではなく実測で示す）。remote と手元は **union** を取る（前回 push に失敗して
    手元にしか無い行を黙って捨てない＝ルール7の親戚）
  - 〔経緯は書庫〕なぜ Actions ではなく Routine か（review_runner.sh が claude -p を呼ぶ＝従量課金／実証済みの経路は Routine 側・2026-08-04 に31社を原本直読でFAIL0） → docs/CLAUDE_ARCHIVE.md L14647
  - **品質はセッションの出来不出来に依存させない**——(1)`validate_packs.py` が FAIL なら**そのパックを捨てる**
    (2)**main へ直接書かず PR**（マージが審査官の手） (3)投下可が動いたら**PR本文で名指し**(v9.9.52)。
    review.yml の三重の縛りをそのまま手順書に写してある
  - **⚠ この Routine は MCP コネクタを持たない**（作成元セッションが渡せる grant を持っていなかった）。
    実害は小さい——**2026-07-28の方針が既に「EDINET_DB MCP には依存しない・原本PDF優先」**なので手順書もそう書いた。
    EDINET_DB を使わせたいなら claude.ai の Routines UI から作り直す必要がある
  - **並列サブエージェントを禁じてある**——2026-08-04 に5班並列でセッション上限に当たった実績があるため。5社を直列で処理する。
    **1社終わるごとに納品検査を通してコミットする**＝途中で上限に当たっても済んだ分が消えない
    （5社に届かないことは失敗ではない、と手順書に明記した）
  - 〔経緯は書庫〕速さの天井は容量ではなく供給（待ち行列67社のうち63社は一度きりの積み残し・定常到着は3週間で4件） → docs/CLAUDE_ARCHIVE.md L14657
